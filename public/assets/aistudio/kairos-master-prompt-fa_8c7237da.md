# پرامپت جامع مهندسی و بازطراحی کایروس

## راهنمای استفاده برای دانیال

این فایل را همراه آخرین سورس کامل پروژه در Google AI Studio بارگذاری کن. لینک گیت‌هاب به‌تنهایی جای دسترسی واقعی به فایل‌های پروژه را نمی‌گیرد. همهٔ متن زیر یک مشخصات جامع است؛ اجرای آن باید مرحله‌ای باشد. در اولین نوبت فقط فاز صفر و فاز یک اجرا شوند. بعد از بررسی خروجی، برای ادامه بنویس: «طبق همین مشخصات و گزارش وضعیت، فقط فاز بعدی را اجرا کن.»

فایل‌های HTML، CSS و JavaScript ساخته‌شده و تصاویر و فونت‌ها به دوست سازندهٔ اندروید تحویل می‌شوند؛ JavaScript با Java اندروید متفاوت است. تأیید بسته‌بندی فایل‌ها در APK، تأیید پیاده‌سازی SQLite، بکاپ یا اعلان بومی نیست.

# شروع پرامپت قابل ارسال به هوش مصنوعی

تو مسئول مهندسی نرم‌افزار، معماری داده، توسعهٔ React/TypeScript، طراحی UI/UX، دسترس‌پذیری و آماده‌سازی چندسکویی پروژهٔ Kairos هستی. تغییرات را واقعاً در سورس موجود پیاده‌سازی کن؛ به توصیه، ماکاپ ثابت یا توضیح کلی اکتفا نکن. این سند هدف نهایی پروژه است، اما اجرای یک‌بارهٔ همهٔ مراحل مجاز نیست.

## ۱. زمینه، هدف و محدودیت‌های قطعی

- پروژهٔ فعلی: https://github.com/Danielprogramming18/kairos-app
- نسخهٔ وب فعلی: https://danielprogramming18.github.io/kairos-app/
- نسخهٔ مبنای بررسی قبلی: 3cfb2b60f8fe9449c0c2be295719e12691583c79. این شناسه فقط سابقهٔ بررسی است؛ آخرین سورس تحویل‌شده را مبنا بگیر و تفاوت‌ها را بررسی کن. باگ‌های این سند فرضیه‌های مشخص برای تأیید روی سورس جدیدند، نه حکم قطعی دربارهٔ هر نسخهٔ آینده.
- برنامهٔ مدیریت فردی شامل کارها، عادت‌ها، تقویم، تمرکز، یادداشت‌ها، ایده‌ها و گزارش است.
- خروجی اصلی اندروید APK/AAB نصب‌شدنی و ویندوز نصب‌کنندهٔ EXE/MSI است. نسخهٔ مرورگر برای توسعه و پیش‌نمایش هم باید باقی بماند.
- اندروید را همکار کاربر با Sketchware یا Sketchware Pro بسته‌بندی می‌کند. فایل‌های build وب باید داخل APK باشند؛ فقط بازکردن URL سایت کافی نیست.
- روش دقیق بسته‌بندی ویندوز هنوز نهایی نشده است. Tauri 2 گزینهٔ پیش‌فرض پیشنهادی است، اما تا تأیید پوستهٔ نهایی، رابط را به API اختصاصی آن وابسته نکن. هم‌زمان چند پوستهٔ دسکتاپ نساز.
- React/TypeScript فعلی حفظ شود. بازنویسی رابط به Flutter، React Native یا صفحات بومی اندروید جزو این درخواست نیست.
- نسخهٔ اول آفلاین، بدون حساب، بدون سرور اختصاصی، بدون Firebase و بدون سرویس همگام‌سازی است. اطلاعات کاربر نباید خودکار به GitHub، تحلیل‌گر، سرویس AI یا مقصد دیگری ارسال شوند.
- تمام منابع ضروری از جمله فونت، آیکون، تصویر و فایل اجرایی داخل بسته باشند. شروع و استفادهٔ اصلی نسخهٔ نصبی پس از نصب، حتی بدون اولین اتصال اینترنت، باید کار کند.
- هیچ قابلیت بومی را فقط به دلیل اجرای موفق در پیش‌نمایش وب «تکمیل‌شده» اعلام نکن. اگر محیط اجرا یا ابزار ساخت نیست، کد و دستور ساخت و قرارداد اتصال را بده و آزمون انجام‌نشده را صریح گزارش کن.
- داده‌های موجود کاربر حفظ شوند. بدون مهاجرت امن، هیچ کلید localStorage، دیتابیس یا اطلاعات واقعی پاک نشود.
- هدف محصول: برنامه‌ریزی روزانهٔ آرام، ثبت سریع و دقیق، فارسی و تقویم شمسی باکیفیت، تمرکز متصل به کار و مالکیت کاربر بر داده.

## ۲. شیوهٔ کار و کنترل تغییرات

۱. ابتدا تمام سورس و تنظیمات واقعی در دسترس را بررسی کن. اگر سورس کامل در دسترس نیست، دقیقاً فایل‌های لازم را مشخص کن؛ کد را از روی تصویر یا توضیح حدس نزن.
۲. قبل از تغییر، وضعیت ساخت، بررسی نوع‌ها و تست‌های موجود را ثبت کن. موفقیت قبلی ۱۵ تست به معنی پوشش همهٔ سناریوها نیست.
۳. در docs فایل‌های architecture.md، implementation-plan.md، audit-status.md، platform-contract.md و acceptance-tests.md بساز و به‌روز نگه دار. وضعیت هر الزام: pending / implemented / verified / blocked / deferred باشد.
۴. هر مرحله تغییر کوچک، قابل بررسی و قابل برگشت داشته باشد. اگر گیت در دسترس است checkpoint مناسب بساز؛ در غیر این صورت فهرست فایل‌های تغییرکرده و روش برگشت را بده.
۵. تست را برای رفتارهای مهم، حفظ داده و باگ‌های واقعی بنویس، نه صرفاً برای تکرار پیاده‌سازی.
۶. نسخهٔ کتابخانه‌ها را با محیط واقعی سازگار انتخاب و lockfile را نگه دار. از نصب بی‌دلیل چند state manager یا چند دیتابیس جلوگیری کن.
۷. بخش‌های سالم و قابلیت‌های موجود را حفظ کن مگر اینکه در این سند جایگزینی‌شان مشخص شده باشد.
۸. در پایان هر فاز: تغییرات، نتیجهٔ واقعی آزمون‌ها، محدودیت‌ها، فایل‌های مهم و گام بعدی را گزارش کن. ادعای اجرای تست یا ساخت APK/EXE بدون اجرای واقعی ممنوع است.
۹. به علت بزرگی کار، فقط فاز مجاز جاری را اجرا کن؛ فازهای بعدی را بی‌خبر آغاز نکن.

## ۳. معماری مشترک و جداسازی پلتفرم

ساختار پیشنهادی را با مقیاس واقعی پروژه تطبیق بده:

```text
src/
  app/                 # مسیریابی، ترکیب وابستگی‌ها، پوستهٔ اصلی
  domain/              # مدل‌ها، قوانین تاریخ، کار، عادت و تمرکز
  application/         # عملیات کاربردی و قرارداد repository/service
  features/            # today, tasks, calendar, habits, focus, notes, insights, settings
  infrastructure/
    web/               # IndexedDB/Dexie برای پیش‌نمایش مرورگر
    android/           # adapter ارتباط با bridge اندروید
    desktop/           # adapter پوستهٔ دسکتاپ منتخب
  shared/ui/           # عناصر مشترک قابل دسترس
  shared/i18n/         # ترجمه و قالب‌بندی
docs/
```

- صفحات هیچ دسترسی مستقیم به localStorage، SQLite، window.Android، Tauri API یا فایل سیستم نداشته باشند.
- قراردادهای مستقل TaskRepository، HabitRepository، NoteRepository، FocusRepository، SettingsRepository، BackupService، NotificationService و AppLifecycleService تعریف کن.
- تزریق وابستگی در نقطهٔ شروع برنامه انجام شود؛ در هر جلسه فقط یک منبع اصلی ذخیره‌سازی فعال باشد.
- در مرورگر adapter واقعی IndexedDB با Dexie استفاده شود. حافظهٔ موقت فقط برای تست؛ نباید به‌جای ذخیرهٔ دائمی معرفی شود.
- در اندروید نسخهٔ نهایی از SQLite در فضای خصوصی برنامه، از طریق bridge محدود و نسخه‌دار استفاده کند. پیاده‌سازی بومی بر عهدهٔ همکار اندروید است، مگر محیط امکان ساخت و اجرای آن را داشته باشد.
- در ویندوز SQLite در پوشهٔ دادهٔ کاربر، خارج از پوشهٔ نصب، و از طریق هستهٔ پوستهٔ انتخاب‌شده استفاده شود.
- فقط ذخیره‌سازی هستهٔ داده platform-specific نباشد: انتخاب/ذخیره/اشتراک فایل، اعلان، بازگشت، رویدادهای pause/resume و وضعیت قابلیت‌ها هم adapter داشته باشند.
- نبود bridge در نسخهٔ بومی باعث fallback پنهانی به دیتابیس دیگر نشود؛ خطای قابل اقدام یا حالت صریح اعلام شود. در پیش‌نمایش وب، adapter وب عمداً انتخاب شود.
- پردازش‌های اصلی رابط و قوانین محصول مشترک باشند؛ اعتبارسنجی ضروری در مرز بومی هم تکرار شود.
- برای این معماری سرور Express روی localhost یا API اینترنتی لازم نیست.

### قرارداد bridge اندروید و دسکتاپ

قرارداد JSON نسخه‌دار و asynchronous طراحی کن. درخواست‌ها requestId، version، operation و payload داشته باشند؛ پاسخ‌ها requestId، ok، result یا error ساختاریافته. timeout، رد نسخهٔ ناسازگار، محدودیت حجم ورودی و قابلیت‌های پشتیبانی‌شده مشخص باشند.

عملیات نمونه: tasks.list/create/update/complete/trash/restore، habits.checkIn/uncheck، focus.start/pause/resume/finish، backup.export/importPreview/importCommit و settings.get/update. ذخیرهٔ مرتبط باید در سمت میزبان تراکنشی باشد. برای retry عملیات حساس، جلوگیری از تکرار ناخواسته با شناسهٔ عملیات در نظر بگیر.

اجازهٔ arbitrary SQL، اجرای فرمان سیستم یا خواندن مسیر دلخواه به JavaScript نده. UI فقط عملیات مجاز محصول را درخواست کند. پیام دریافتی از فریم/مبدأ ناشناس رد شود. API یا پلاگین خیالی نساز؛ نسخهٔ واقعی Sketchware و امکان افزودن کد/کتابخانه باید توسط همکار بررسی شود.

## ۴. مدل داده و ذخیره‌سازی

دیتابیس منبع اصلی حقیقت باشد. state رابط برای نمایش/تعامل است، نه نسخهٔ مستقل دائمی داده. در وب IndexedDB و در اپ نصبی SQLite پیاده‌سازی شوند و تست‌های قراردادی مشترک داشته باشند.

جدول‌ها/مجموعه‌ها:

- tasks: id، title، description، projectId اختیاری، dueDate اختیاری برای Inbox، scheduledStart اختیاری، estimatedMinutes، priority، status، completedAt، reminder مشخص و timestamps.
- projects: id، name، archivedAt و timestamps.
- habits: id، title، category، emoji اختیاری، colorToken، startDate، schedule، weeklyGoal، paused/archived و timestamps.
- habit_entries: id، habitId، localDate، status مانند done/skipped، timestamps؛ کلید یکتای habitId+localDate.
- notes: id، title، body، type شامل idea/note/link/code، tags، pinned، linkedTaskId اختیاری و timestamps.
- focus_sessions: id، taskId اختیاری، start/end، زمان فعال واقعی، وضعیت کامل/نیمه‌تمام و timezone لازم.
- active_timer: وضعیت ماشین حالت تایمر، sessionId، taskId، endAt یا remainingAtPause، accumulatedActiveMs و تنظیمات جلسه؛ حداکثر یک جلسهٔ فعال طبق سیاست روشن.
- settings، drafts، recovery_snapshots و metadata/schema_migrations.

اصول:
- UUID برای شناسه، نه صرف Date.now().
- createdAt و updatedAt، revision و deletedAt برای موجودیت‌های قابل حذف. حذف عادی نرم باشد؛ پاک‌سازی دائمی جریان جدا دارد.
- timestamp رویدادها UTC؛ موعد روزانهٔ بدون ساعت یک localDate باشد. تبدیل خودکار تاریخ روزانه به نیمه‌شب UTC نکن. منطقهٔ زمانی IANA، شروع هفته، تقویم و قالب ساعت تنظیم مستقل دارند.
- تاریخ نمایشی فارسی را به‌عنوان کلید اصلی ذخیره نکن. تغییر تقویم نمایش نباید معنای تاریخ موجود را تغییر دهد.
- دادهٔ مشتق‌شده مثل درصد و streak تا حد امکان محاسبه شود؛ تعریف آن در domain مشترک باشد.
- ورودی‌های فارسی/عربی/انگلیسی نرمال شوند. محدودیت طول متن، مدت، اولویت و تعداد رکورد در import تعریف شود.
- عملیات چندرکوردی تراکنشی، خطای ذخیره قابل نمایش و قابل بازیابی باشد. موفقیت فقط بعد از commit واقعی.
- ویرایش هم‌زمان چند تب/پنجره با revision و اطلاع‌رسانی تغییرات کنترل شود؛ آخرین آرایهٔ قدیمی بی‌خبر روی دادهٔ جدید نوشته نشود.
- schema migration نسخه‌دار، قابل آزمون و بدون reset کورکورانه باشد. ارتقای شکست‌خورده اطلاعات قبلی را نگه دارد.
- برای SQLite از foreign key، constraint و index متناسب استفاده کن. سیاست journal/durability را مستند و با کتابخانهٔ میزبان سازگار کن؛ تضمین غیرواقعی در برابر هر خرابی سخت‌افزار نده.

### مهاجرت داده‌های فعلی

کلیدهای واقعی nazmyar و ساختار موجود را از سورس پیدا کن. نسخهٔ خام قابل بازیابی تهیه کن؛ parse و schema validation انجام بده؛ رکوردهای ناسازگار را با گزارش کنار بگذار و بی‌صدا دور نریز. دادهٔ معتبر در تراکنش وارد شود، شمارش و ارتباط‌ها بررسی شوند و سپس marker مهاجرت نوشته شود. مهاجرت idempotent باشد. منبع قدیمی تا تأیید موفقیت و دسترسی به بکاپ حفظ شود.

انتقال دادهٔ مرورگر به APK یا EXE خودکار فرض نشود؛ ذخیره‌سازی این محیط‌ها جداست. برای کاربران قبلی مسیر export/import معتبر فراهم کن. تاریخ شروع تاریخیِ نامعلوم عادت را با ادعای دقیق اختراع نکن؛ وضعیت legacy و سیاست محاسبه را شفاف مدیریت کن.

## ۵. بکاپ، بازیابی و حذف

- قالب قابل انتقال و مستقل از موتور دیتابیس داشته باش: appId، formatVersion، exportedAt، schemaVersion و data.
- خروجی تمام کارها، عادت‌ها، تاریخچه، یادداشت‌ها، پروژه‌ها، جلسات و تنظیمات قابل انتقال را پوشش دهد؛ رمز، توکن، مسیر اختصاصی دستگاه و وضعیت ناسازگار تایمر فعال کورکورانه منتقل نشوند.
- قبل از import، حجم، نوع و نسخه، شناسه‌های تکراری، مقادیر نامعتبر و ارتباط رکوردها بررسی شود.
- preview تعداد رکوردها و اثر جایگزینی را نشان بده. نسخهٔ اول restore با replace شفاف است؛ merge ناقص و مخفی نساز.
- قبل از replace از وضعیت موجود snapshot بگیر. اعمال داده تراکنشی باشد؛ آرایهٔ خالی واقعاً بخش متناظر را خالی کند.
- فایل خراب، نسخهٔ جدیدِ پشتیبانی‌نشده یا رمز اشتباه هیچ تغییری در دادهٔ جاری ندهد.
- recovery snapshot داخلی محدود و گردشی باشد؛ آن را بکاپ مستقل در برابر پاک‌شدن کل برنامه معرفی نکن.
- خروجی مستقل در محل انتخابی کاربر، زمان آخرین بکاپ و یادآوری قابل خاموش‌کردن فراهم کن. فایل‌های خصوصی اندروید ممکن است با uninstall/clear data حذف شوند؛ خروجی باید خارج از آن قابل نگهداری باشد.
- بکاپ زندهٔ SQLite با API مناسب یا export منسجم انجام شود، نه کپی سادهٔ فایل در حین نوشتن و نادیده‌گرفتن journal/WAL.
- بکاپ رمزگذاری‌شدهٔ اختیاری با primitive استاندارد و کتابخانهٔ معتبر، رمز مشتق‌شده از گذرواژه، salt تصادفی و nonce یکتا طراحی کن. فرمت رمزگذاری و پارامترهای KDF نسخه‌دار باشند؛ بین وب و موبایل و دسکتاپ تست سازگاری داشته باشند. الگوریتم اختراعی، کلید ثابت داخل کد و ذخیرهٔ گذرواژه کنار فایل ممنوع.
- فراموشی رمز بکاپ را صریح توضیح بده. checksum معمولی را به‌جای تأیید اصالت رمزنگاری معرفی نکن.
- حذف نرم، Undo و سطل زباله فراهم شود؛ حذف دائمی با توضیح اثر و تأیید کاربر.

## ۶. سیاست آفلاین و همگام‌سازی

- GitHub sync و ورود PAT از تجربهٔ اصلی نسخهٔ اول حذف/غیرفعال شوند؛ دادهٔ موجود قبلاً export و مهاجرت شود و token قدیمی بی‌خبر استفاده نشود.
- اگر کد sync قدیمی برای سابقه می‌ماند، به‌صورت غیرقابل فعال‌سازی در محصول جدید نگه دار. ذخیرهٔ امن کد قدیمی با ارائهٔ قابلیت فعال تفاوت دارد.
- دستگاه‌ها مستقل‌اند. جابه‌جایی دستی بکاپ «همگام‌سازی» نام نگیرد. ویرایش هم‌زمان دو دستگاه به‌طور خودکار ادغام نمی‌شود.
- معماری repository قابل گسترش باشد، ولی CRDT، سرور sync یا outbox پیچیده را بدون نیاز فعلی نساز.
- اگر در آینده sync اضافه شد، قبل از فعال‌سازی باید حذف با tombstone، لغو تیک، تغییر هم‌زمان، اولین اتصال، تغییر مخزن و dirty local state حل شوند؛ union سادهٔ آرایه‌ها مجاز نیست.
- در نسخهٔ وب Service Worker می‌تواند برای preview/offline وب استفاده شود. در بستهٔ بومی، اجرای منابع محلی نباید به Service Worker وابسته باشد؛ از تداخل cache وب و آپدیت بومی جلوگیری کن.

## ۷. فهرست باگ‌ها و اصلاحات لازم

## ۸. معماری اطلاعات و مسیرها

موبایل پنج مقصد ثابت پایین: امروز، کارها، تقویم، عادت‌ها، بیشتر. روی دسکتاپ همان ساختار در sidebar و تنظیمات پایین باشد. نوار ۱۱تایی افقی فعلی حذف شود. آیتم‌های کم‌استفاده پشت منوی ثانویه باشند، بدون پنهان‌کردن کارهای اصلی.

مسیرهای معنایی:
- /today
- /tasks با زیرنماهای inbox، all، upcoming، projects و completed
- /tasks/:id برای جزئیات
- /calendar با view=date/week/month/year و تاریخ انتخابی
- /habits و /habits/:id
- /focus برای نمای خلوت جلسه
- /notes با فیلتر ideas/notes/links/code
- /insights برای گزارش
- /settings با appearance، language-region، data-backup، notifications، accessibility و about
- /trash

در بستهٔ فایل محلی، HashRouter یا راهکار سازگار با میزبان استفاده کن؛ route ظاهراً درست ولی پس از reload خراب نباشد. Back اندروید ابتدا modal، سپس جزئیات/مسیر را ببندد؛ از صفحهٔ ریشه رفتار خروج روشن باشد. back مرورگر هم درست کار کند.

تایمر فعال mini-player ثابت در تمام صفحات داشته باشد، با فاصلهٔ کافی از bottom navigation و safe area. «تمرکز» عمل روی کار است، نه مقصدی که پیدا کردنش دشوار باشد. دستیار محلی به‌صورت ابزار زمینه‌ای/پنل کمکی یا گزینهٔ بیشتر در دسترس باشد و ضرورتاً مقصد اصلی نشود.

مسیرهای اصلی:
۱. افزودن → عنوان → ذخیره؛ date/project/priority/duration اختیاری و تدریجی.
۲. امروز → کار مهم بعدی → شروع تمرکز.
۳. کار → زمان‌بندی → تقویم همان روز.
۴. عادت‌ها → ثبت یک‌لمسی → Undo.
۵. تنظیمات → داده‌ها → export/import → preview → تأیید.
۶. ایده → ویرایش → تبدیل به کار → پیوند به کار ساخته‌شده.

## ۹. طراحی صفحه‌ها

### امروز
ابتدا تاریخ و افزودن سریع، سپس «کار مهم بعدی»، کارهای امروز و بخش جدا برای عقب‌افتاده‌های ناتمام. عادت‌های امروز بعد از کارها. آمار کوتاه پایین‌تر؛ چهار KPI بزرگ پیش از عمل اصلی نباشند. تکمیل‌شده‌های امروز جمع‌شدنی باشند. ظرفیت زمانی روز و مجموع مدت تخمینی واضح و قابل تنظیم باشند؛ بیش‌برنامه‌ریزی با لحن حمایتی نشان داده شود.

### کارها
Inbox بدون تاریخ اجباری، جست‌وجو، فیلتر، پروژه، ویرایش جزئیات، انتخاب چندتایی و زمان‌بندی. اولویت چهار سطح قابل فهم با نگاشت مستند از ۱..۲۰ قدیمی؛ در صورت نیاز ترتیب امروز جدا از priority ذخیره شود. مدت تخمینی و زمان واقعی دو مفهوم جدا باشند. عملیات گروهی scope روشن، preview و Undo مناسب داشته باشند.

### تقویم
نمای روز/هفته برای استفادهٔ روزانه، ماه برای برنامه‌ریزی و سال فرعی. تغییر سال، امروز، انتخاب تاریخ و نمایش جزئیات هماهنگ. روز بدون کار حالت خالی مفید داشته باشد. Drag & drop اگر اضافه شد، تنها راه زمان‌بندی نباشد؛ کنترل قابل دسترس هم وجود داشته باشد.

### تمرکز
در حالت عمیق، منو و تزئینات اضافی جمع شوند. یک کار، زمان، pause/resume/finish و یادداشت سریع. پیش‌تنظیم‌های فعلی حفظ و مدت سفارشی اضافه شود. پایان زودهنگام زمان واقعی را با تأیید ثبت کند. تغییر روز و resume از پس‌زمینه درست محاسبه شوند. تغییر ساعت دستگاه را در طراحی و تست لحاظ کن؛ شمارش UI جای منبع زمان معتبر نیست.

### عادت‌ها
ابتدا موارد امروز؛ روی گوشی کارت‌های مناسب لمس، روی دسکتاپ جدول هفتگی اختیاری. ساخت/ویرایش عنوان، دسته، آیکون، رنگ، روزهای هفته یا تعداد هدف، تاریخ شروع، یادآور و توقف/بایگانی. قوانین streak برای عادت هرروزه و هدف هفتگی صریح باشند؛ روز استراحت شکست خودکار محسوب نشود. تاریخچه و نمودار پس از عمل اصلی.

### یادداشت‌ها و ایده‌ها
یک مقصد با فیلتر نوع. ویرایش چندخطی، جست‌وجو، pin، archive، copy و trash. لینک امن، متن RTL/LTR درست و قطعه‌کد monospace. تغییر نوع/دسته و تبدیل ایده به کار تاریخچهٔ ارتباط را حفظ کند. pin default در create/reset سازگار باشد.

### دستیار محلی
قواعد موجود را صادقانه «دستیار محلی» معرفی کن. بدون اتصال واقعی ادعای Gemini یا فهم عمومی نکن. پیش‌نویس گفت‌وگو و ویزارد حفظ، مراحل قابل ویرایش و پیشنهادها پیش از اعمال قابل بازبینی باشند. هیچ درخواست API ضروری برای کارکرد آفلاین ایجاد نکن. مدل بزرگ آفلاین را خودسرانه به بسته اضافه نکن.

### گزارش
بازهٔ صریح این هفته/۷ روز گذشته/انتخابی، انجام کار بر مبنای completedAt، زمان تخمینی و واقعی جدا، نرخ عادت متناسب schedule/startDate. streak جاری و تاریخی جدا. امکان کپی و خروجی با نتیجهٔ واقعی. آمار جعلی و نام ثابت دانیال حذف شود.

### تنظیمات و شروع کار
شروع خالی با راهنمای کوتاه و نمونهٔ اختیاری جدا. ورود اجباری، ساخت توکن، راهنمای انتشار GitHub و اصطلاحات توسعه‌دهنده از مسیر کاربر عمومی حذف شوند. زبان، تقویم، شروع هفته، ساعت، صدا، motion، تم، ذخیره/بکاپ، حریم خصوصی و دربارهٔ برنامه در تنظیمات باشند. توضیح واضح: داده روی همین دستگاه است و انتقال خودکار بین دستگاه‌ها وجود ندارد.

- emoji انتخابی عادت حفظ شود؛ برای هر دکمه استیکر/ایموجی اضافی نگذار. جشن بزرگ فقط محدود و اختیاری؛ صدا و motion قابل خاموش‌کردن.
- theme روشن/تاریک/سیستم واقعی؛ Tailwind variant با روش انتخاب تم هماهنگ شود.

متن‌ها: «داشبورد هوشمند» به «امروز»، «میز کار و مأموریت‌ها» به «کارها»، «پارکینگ ایده‌های دانیال» به «ایده‌ها»، «اطلاعات کاربردی» به «یادداشت‌ها و منابع». برند کایروس/Kairos در title، manifest، گزارش و رابط یکدست شود. عبارت‌های NLP و SHA در تجربهٔ عمومی نمایش داده نشوند. به‌جای وعدهٔ فهم هر جمله، نمونه و preview بده. لحن حمایتی و کوتاه، بدون سرزنش یا ادعای پزشکی.

## ۱۱. واکنش‌گرایی، بومی‌سازی و دسترس‌پذیری

- موبایل یک‌ستونه، bottom nav، safe-area و keyboard insets؛ فرم طولانی sheet تمام‌ارتفاع/صفحه با scroll داخلی و دکمهٔ قابل دسترسی.
- تبلت در صورت فضای کافی list/detail؛ دسکتاپ sidebar و پنل جزئیات. breakpoint بر اساس محتوا، نه صرف نام دستگاه.
- در عرض ۳۲۰،۳۶۰،۳۹۰،۷۶۸،۱۰۲۴،۱۴۴۰ و بزرگ‌نمایی ۲۰۰٪ آزمون کن؛ overflow افقی کل صفحه نباشد.
- حذف یا عملیات ضروری فقط hover نباشند. متن بلند قابل خواندن/گسترش باشد، نه truncate دائمی.
- HTML معنایی، label مرتبط، نام دکمهٔ آیکونی، aria-selected/pressed مناسب، پیام ذخیره/خطا با live region غیرمزاحم.
- dialog با focus اولیه، focus trap، Escape، بازگشت focus و هشدار مناسب برای draft ذخیره‌نشده. کلیک بیرون متن طولانی را بی‌خبر پاک نکند.
- focus ring واضح، کیبورد کامل، کاهش motion، عدم اجبار صدا و عدم تکیه به رنگ.
- حداقل کنتراست متن معمولی 4.5:1 و متن درشت واجد شرایط 3:1؛ کنترل‌ها و focus هم طبق معیار مربوط بررسی شوند. border تزئینی را با مرز ضروری کنترل اشتباه نگیر.
- تمام متن‌ها در منابع ترجمه، fa و en؛ جهت صفحه مستقل از جهت code/URL. تقویم، ارقام، شروع هفته و ساعت مستقل از زبان.
- تاریخ native میلادی در فرم فارسی بدون توضیح نماند؛ date picker متناسب تقویم و ورودی قابل دسترس فراهم کن.

## ۱۲. امنیت و حریم خصوصی

- محتوای کاربر به‌صورت متن امن نمایش داده شود؛ HTML خام اجرا نشود. rich text تنها با sanitization معتبر و allowlist لازم.
- لینک‌ها فقط scheme مجاز؛ javascript: و مسیرهای خطرناک رد شوند. لینک خارجی بیرون WebView دارای bridge باز شود.
- همهٔ ورودی‌های import و bridge، حتی دادهٔ خوانده‌شده از دیتابیس، اعتبارسنجی شوند. JSON parse بدون schema کافی نیست.
- query پارامتری؛ عدم SQL رشته‌سازی‌شده از ورودی کاربر.
- CSP متناسب محیط وب/بومی؛ هیچ eval یا مجوز گستردهٔ بی‌دلیل. dev-only تنظیمات در release نباشند.
- دسترسی فایل و قابلیت‌های بومی least privilege. bridge نباید برای صفحات اینترنتی، iframe ناشناس یا navigation دلخواه قابل استفاده باشد.
- فایل‌های محلی اندروید ترجیحاً با WebViewAssetLoader و مبدأ ثابت مدیریت شوند. برای رفع خطا universal file access یا mixed content گسترده فعال نکن. هر وابستگی لازم با نسخهٔ واقعی Sketchware بررسی شود.
- SQLite عادی رمزگذاری‌شده نیست. قفل PIN صرفاً ظاهری را رمزگذاری دیتابیس معرفی نکن. رمزگذاری کامل دیتابیس و مدیریت کلید موضوع جداست و اگر پیاده نشده، صریح اعلام شود.
- داده و رمز/token در log نریز. لاگ تشخیصی محلی حداقلی و export آن با اقدام کاربر.
- هیچ telemetry یا SDK تبلیغاتی پیش‌فرض اضافه نکن. ارسال محتوای کاربر و AI آنلاین خارج از scope است.
- فایل‌های شخصی اولیه، نام ثابت دانیال، برنامهٔ مدرسه/فروشگاه و فایل HTML قدیمی حاوی دادهٔ نمونهٔ شخصی از بستهٔ عمومی حذف یا با دادهٔ عمومی اختیاری جایگزین شوند؛ دادهٔ کاربر موجود حذف نشود.
- وابستگی‌های استفاده‌نشده، از جمله SDK ابریِ بدون استفاده، پس از بررسی حذف شوند. dependency audit اجرا و محدودیت آن گزارش شود؛ صفرشدن هشدار audit معادل تست نفوذ نیست.
- امضا و کلید انتشار در سورس عمومی نباشد. کلیدهای signing به کاربر/سازندهٔ بومی تعلق دارند؛ کلید ساختگی production تولید و منتشر نکن.

## ۱۳. تحویل اندروید و ویندوز

### اندروید Sketchware
بستهٔ frontend production شامل index.html، JS/CSS ساخته‌شده، تصاویر، آیکون و فونت محلی، راهنمای مسیرها، مجوز منابع و شمارهٔ نسخه تحویل بده. JavaScript را Java معرفی نکن. assets با مسیر پایهٔ سازگار resolve شوند. route و reload در میزبان محلی درست کار کنند.

docs/ANDROID_HANDOFF.md شامل این موارد باشد: نسخهٔ قرارداد bridge؛ درخواست/پاسخ و خطاها؛ schema منطقی SQLite و migration؛ نحوهٔ خواندن assets؛ Back/keyboard/safe area؛ انتخاب/ذخیرهٔ فایل؛ اعلان و لغو/باززمان‌بندی آن؛ تنظیم backup سیستم‌عامل با تصمیم آگاهانه؛ الزامات build/signing بدون ادعای انجام آن؛ آزمون‌های روی دستگاه.

بسته‌بندی دوست سازنده فقط فایل‌ها را داخل APK قرار می‌دهد مگر اتصال‌ها عملاً تأیید شوند. اگر bridge ندارد، اعلام کن نسخهٔ SQLite native آمادهٔ استفاده نیست. IndexedDB داخل WebView می‌تواند حالت موقتِ صریح برای نمونه باشد، نه جایگزین پنهانی قرارداد نهایی.

نمونهٔ زودهنگام باید: بدون اینترنت از نصب تازه باز شود، یک task در SQLite بنویسد، پس از force-stop بخواند و یک backup قابل بازیابی بدهد. این آزمون قبل از بازطراحی گسترده انجام یا به‌عنوان مانع مشخص ثبت شود.

### ویندوز
پوستهٔ منتخب با منابع محلی، SQLite در AppData مناسب، حداقل مجوز، backup picker، update/migration امن و installer آماده شود. اگر Tauri انتخاب شد، فرمان‌های محدود و capability مناسب، بدون remote page دارای دسترسی بومی. برای نصب آفلاین، وابستگی WebView2 و اندازه/روش توزیع آن تصمیم‌گیری شود.

docs/WINDOWS_HANDOFF.md ابزارهای ساخت، دستور build، محل خروجی، رفتار آپدیت و uninstall، signing و محدودیت آزمون را توضیح دهد. EXE ساخت‌نشده را فایل آماده معرفی نکن. نیاز نداشتن به سرور با نیاز داشتن به ابزار build متفاوت است.

## ۱۴. تست‌ها و معیار پذیرش نهایی

تست unit برای domain، integration برای repository و migration/backup، contract برای هر adapter و E2E برای مسیرهای اصلی بنویس. تست بومی فقط روی محیط واقعی یا emulator معتبر تأیید شود.

- تست‌های فعلی مفید حفظ شوند؛ رگرسیون‌های جدول BUG اضافه شوند.
- task بدون تاریخ، ساخت/ویرایش/تکمیل/Undo/trash/restore؛ حفظ category و تاریخ درست.
- habit جدید در میانهٔ هفته، هدف ۳ روز، روز استراحت، pause/archive، لغو تیک، عدم ثبت آینده.
- report برای کار با موعد قدیمی و تکمیل امروز؛ تفاوت هفتهٔ جاری و ۷ روز؛ زمان تخمینی در برابر واقعی.
- timer: تعویض صفحه، refresh، pause/resume، بستن اجباری، بازگشت پس‌زمینه، پایان جزئی، تغییر کار، نیمه‌شب و تغییر ساعت.
- parser: مثال‌های BUG-22..25، فارسی/عربی/لاتین، ورودی مبهم و عدم ادعای تشخیص قطعی.
- backup: round-trip تمام داده‌ها، آرایهٔ خالی، فایل خراب، نسخهٔ ناسازگار، شناسهٔ تکراری، حجم بیش از حد، رمز اشتباه و تراکنش شکست‌خورده.
- migration: دادهٔ قدیمی معتبر، ناقص و خراب؛ اجرای دوباره بدون duplicate؛ شکست وسط کار بدون از دست رفتن منبع.
- storage: فضای ناکافی، شکست write و تغییر هم‌زمان دو تب/پنجره؛ موفقیت کاذب نمایش داده نشود.
- امنیت: متن HTML/script به‌صورت بی‌خطر، لینک javascript ردشده، پیام bridge ناشناس/بزرگ/ناقص ردشده، عدم network exfiltration خودکار.
- UI: light/dark/system، RTL/LTR، متن بلند، ارقام، screen reader smoke test، کیبورد، بزرگ‌نمایی، موبایل افقی و keyboard باز.
- اندروید/ویندوز: نصب تازه آفلاین، ذخیره بعد از restart، ارتقای نسخه با حفظ داده، export خارج از دادهٔ خصوصی، بازیابی روی نصب دیگر. notification با permission denied و محدودیت پس‌زمینه هم بررسی شود.
- سناریوی بحرانی داده نباید fail بماند. بدون آزمون واقعی، برچسب verified نزن.

## ۱۵. ترتیب اجرای فازها

### فاز صفر: کشف و خط مبنا
خواندن سورس، ثبت build/typecheck/test، تطبیق جدول باگ‌ها، حفظ وضعیت قبلی و ساخت اسناد تصمیم. هیچ بازنویسی کلی انجام نده.

### فاز یک: مرز معماری و نمونهٔ اتصال
قراردادهای repository/platform، جداسازی دسترسی مستقیم از UI، adapter وب با قابلیت واقعی ذخیره و قرارداد میزبان بومی. یک مسیر واقعی «ساخت/خواندن کار» و آزمون قراردادی ایجاد کن. برای تغییر adapter، مهاجرت حداقلی امن لازم را فراهم کن؛ اطلاعات موجود را به دیتابیس خالی تبدیل نکن. prototype بومی و موارد نیازمند همکار را تحویل بده. اگر ابزار بومی موجود نیست، مسدودبودن تست را گزارش کن و کار وب مستقل را کامل کن.

### فاز دو: مدل داده، مهاجرت و بکاپ
مدل‌های نهایی، تراکنش، migration، سطل زباله، خطاهای ذخیره، بکاپ/restore و قرارداد SQLite. GitHub sync فعال از محصول جدید کنار گذاشته شود. تست حفظ داده شرط عبور است.

### فاز سه: اصلاح عملکرد
تایمر، روز/تقویم، آمار، عادت، NLP، draft، ایده و یادآورها طبق جدول BUG. ابتدا correctness سپس تزئین.

### فاز چهار: ساختار صفحات
ناوبری پنج‌مقصدی، sidebar، route، جزئیات، today/inbox/calendar و mini-timer؛ مسیرهای اصلی قابل استفاده شوند.

### فاز پنج: سیستم طراحی و بومی‌سازی
پالت کامل، اندازه‌ها، theme، فرم‌های قابل دسترس، متن‌ها، RTL/LTR و responsive؛ polish بر مبنای اجزای مشترک.

### فاز شش: یکپارچه‌سازی بومی
اتصال‌های واقعی SQLite، backup، اعلان، lifecycle و بسته‌بندی. build و آزمون Android/Windows طبق محیط در دسترس؛ کار باقیماندهٔ همکار دقیق باشد.

### فاز هفت: سخت‌سازی و تحویل
آزمون‌های امنیتی و رگرسیون، بررسی dependency، نصب/آپدیت آفلاین، مستندات کاربر و توسعه‌دهنده، فهرست محدودیت‌ها و release checklist.

## ۱۶. دستور اجرای این نوبت

این سند را نقشهٔ کل پروژه بدان. اکنون فقط فاز صفر و فاز یک را اجرا کن؛ فازهای بعدی را اجرا نکن. خروجی باید کد واقعیِ مرحلهٔ جاری، اسناد و نتیجهٔ آزمون‌های اجراشده باشد. اگر محیطت فقط امکان وب دارد، کار وب و قراردادهای اتصال را تکمیل کن و قابلیت بومی را جعل نکن.

گزارش پایان مرحله را با این ترتیب ارائه کن:
۱. چه چیزی پیاده شد؛ ۲. فایل‌های تغییرکرده؛ ۳. آزمون‌های اجراشده و نتیجه؛ ۴. باگ‌های بسته‌شده با ID؛ ۵. موارد مسدود/تست‌نشده؛ ۶. دستور دقیق برای ادامهٔ فاز بعدی.
